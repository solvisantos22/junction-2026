# Saved Opus autopilot on the four-rule mission

14 November 2026. User-approved next step after the
[prototype assessment](research/2026-11-14-prototype-assessment.md). This is a
free transfer screen first, followed by failure inspection. It does not change
the environment, choose the project or claim a new live-model result.

## Frozen selection and protocol

Select `docs/lightlag-runs/live-oneshot-opus-1/policy.py` before any transfer
scores are inspected. It was the strongest saved Opus program on the earlier
full 200-map comparison, approximately level with the frozen reference. It was
generated by Opus 5.5 at medium effort and contains 678 lines. That comparison
used noise level 2; the new mission uses noise level 1. This preselection is
historical, not chosen by performance on the new rule changes.

The program is copied unchanged into an isolated Docker worker. Only the five
public tools cross the process boundary. No simulator code, seed, hidden change
or evaluator files are mounted. Thinking does not advance simulation time.
The policy can read the complete public menu, although its saved code currently
does not consume it. The reference gets the same public information.

- `rush_noisy`, delay 3, horizon 50, noise level 1.
- Already-consumed seeds **3200–3239**, each forced to `ground`, `turning`,
  `link` and `relay`: 160 changed episodes per policy.
- The same 40 seeds with unchanged `DynamicEnvironment` provide a transfer
  control. This control has no change menu, so it is not a same-contract sham.
- Primary comparator: the existing public-information `Prepared` reference.
  Run it unchanged. Retain its raw and normalized results alongside the model
  program's. The existing stock-controller table remains contextual evidence.
- One fresh worker/process per mission; no policy repair, seed filtering,
  threshold tuning or paid/model call during this screen.
- Retain every case, including crashes, rejected public calls and timeouts.
  Infrastructure failures are identified separately. Finish and grade the full
  horizon even if a policy returns early; early return is not automatic success.
- Record sampled science, raw reward, mean per-episode normalized reward,
  deaths and alive/home counts. Raw reward already includes return/survival
  penalties. Its denominator is available target value, not an exact optimum.
- Cases share 40 seeds across four kinds; report descriptive comparisons,
  not 160 independent statistical observations.

## Decision rule, declared before the full replay

Retire this version for further spending if all cases execute without harness
failures or invalid public calls and the frozen Opus program satisfies all of:

1. Mean normalized reward over the 160 changed episodes is at least
   `Prepared − 0.05`.
2. No kind's mean is more than `0.10` below Prepared.
3. Zero deaths, at least 154/160 alive/home overall, and at least 36/40
   alive/home in every kind.

These are engineering screening thresholds, not a statistical guarantee of
model equivalence. Missing them does not automatically warrant a paid retry.
First inspect whether the deficit is substantive, related to a new rule and
reproducible, rather than an adapter problem or an isolated failure.

## Conditional continuation

If warranted, a bounded adaptation attempt should give the strong model its
original code, the complete rules and used practice cases with feedback. Allow
code, conservative budgeting, tracking acknowledged execution times and handling
missing telemetry. Preserve the actual relay acknowledgement cue. Freeze the
adapted program before a separately declared unused balanced check range.

Record the exact harness, model configuration, source hashes, requests, costs
and stopping limits before making calls. Check the applicable credit budget;
do not treat historical bookkeeping as a live provider balance or consume a
teammate's unrelated allocation. The user authorized this sequence, but the
first step itself launches no paid call.

Even a deficit after that attempt is evidence about a generated program under
this adaptation setup. A general frontier-agent difficulty claim would require
confirmation with the full interactive coding agent. Keep successes and
negative results, and do not expand the environment to force a selected score.
